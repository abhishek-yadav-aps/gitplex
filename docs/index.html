One workspace for repos that ship together.

Gitplex builds a combined working directory for tightly coupled repositories. The editable view lives in workspace; the real clones stay in .gitplex/repos. Preview the exact publish plan, commit and push together or separately, verify remote refs, and recover interrupted operations.

[ 01 ] /why

Monorepo ergonomics. Polyrepo ownership.

Some stacks need separate repositories for ownership, release, or access boundaries, but developers still need to change them as one product. Gitplex gives you a single generated edit surface without pretending the repositories stopped being independent.

without with Gitplex
jump between cloned repos work in one generated tree
manually update dependency refs preview and publish in graph order
risk publishing scratch edits publish only staged workspace files
recreate shell context jump with workspace-mode and repo-mode
restart failed Git operations by hand continue or abort from a durable journal

[ 02 ] /workflow

The working tree has a memory of every repo.

Gitplex keeps a manifest, backing clone state, and generated workspace in sync so the cross-repo edit path stays quick while the publication path stays explicit.

01 INIT

Clone the graph

Strictly validate fields, paths, mappings, and dependency cycles before creating the workspace.

gitplex validate manifest.yaml
gitplex init manifest.yaml
02 CHANGE

Edit together

Inspect ownership, repository-scoped diffs, merged history, status, and affected dependents.

gitplex status --json
gitplex diff --staged
gitplex log --limit 20
03 PLAN

Plan the graph

See dependency edges, calculate the downstream cascade, and preview the exact publish order.

gitplex graph
gitplex affected
gitplex push --dry-run
04 PUSH

Publish intentionally

Commit and push together or separately. Every phase is journaled and every pushed remote ref is verified.

git add app-db app-gateway
gitplex commit -m "ship the change"
gitplex push
# after a rejected push:
gitplex push --resume

01 / START + SYNC

Create a safe workspace

Validate manifests, automatically discover module roots, clone configured refs, fast-forward every backing clone, and regenerate the workspace when required.

init · validate · pull · workspace-mode
02 / INSPECT + OWNERSHIP

Know what owns a file

Inspect state, scoped diffs, merged histories, dependency edges, downstream impact, and the exact backing-repository owner for a workspace path.

status · diff · log · graph · affected · which
03 / BRANCH + HISTORY

Move every repo deliberately

Create a coordinated branch, checkout one or all repositories, rebase onto an upstream branch, cherry-pick a targeted commit, or amend the last workspace-derived commit.

branch · checkout · rebase · cherry-pick · amend
04 / CONFLICT WORKFLOWS

Resolve in the workspace

Rebase and cherry-pick conflicts are surfaced in the generated workspace. Continue repeatedly as Git reaches later commits, or abort and restore every touched repository head.

rebase --continue|--abort · cherry-pick --continue|--abort
05 / COMMIT + PUBLISH

Ship staged intent

Preview affected repositories and dependency order, prepare local commits, push with remote-ref verification, update downstream flake inputs, and resume an interrupted publish.

commit · push · push --dry-run · push --resume
06 / BUILD + TOOLING

Keep the environment close

Build with Nix or without substitutes, run workspace-only stash commands, diagnose project health, navigate through a shell helper, install the VS Code ownership extension, and update Gitplex itself.

build · true-build · stash · doctor · shell-init · repo-mode · install-extensions · update

doctor
Run preflight checks for tools, graph validity, workspace sync, and repository state.

Install the bundled Gitplex ownership extension into VS Code.

Replace the current executable with the latest Gitplex release.

Fast-forward backing repositories and refresh the generated workspace.

Print the shell helper that lets navigation commands change your current directory.

Checkout one repository or all repositories to a branch, then refresh.

[ 04 ] /safety

Designed around the scary parts.

Multi-repo tooling is only useful when it protects the work you did not mean to touch. Gitplex treats generated files, backing clones, and staged intent as separate states.

STAGED ONLY

Push what you selected

Unstaged workspace edits are left alone, and a final refresh is skipped when it would overwrite local work.

DIRTY CHECKS

Refuse risky rewrites

Checkout, rebase, and workspace regeneration stop when the workspace or selected backing repos are dirty.

DEPENDENCIES

Update refs downstream

When dependency repos move, downstream flake inputs and locks can be updated before their commits.

BACKING CLONES

Keep escape hatches

Every real repo remains available under .gitplex/repos for inspection, recovery, and manual diagnosis.

STRICT VALIDATION

Reject unsafe manifests

Unknown fields, reserved paths, overlapping mappings, invalid dependencies, and graph cycles fail early.

DURABLE JOURNALS

Resume exact operations

Per-repository publish phases preserve planned, committed, pushed, failed, and skipped state.

REMOTE VERIFICATION

Prove the push landed

State advances only after the remote branch is confirmed at the journaled commit.

CONFLICT RECOVERY

Continue or roll back

Rebase and cherry-pick conflicts can continue after resolution or restore all touched repository heads.
